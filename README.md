# cybernetics-log

An [eve](https://github.com/vercel/eve) agent that renders a styled HTML page about the **machine-consciousness discourse on X** and how its stance was classified. Data: 268 English posts from 213 authors, 24 Sep – 8 Oct 2026.

The agent **does not classify anything**. Stance labels (hand labels, embeddinggemma-2, Jev via AI Gateway) are produced offline on the analysis box and committed under `data/`. The agent reads that data and writes the editorial copy. Every chart, table, number, quote and link on the page is rendered deterministically from the committed data.

There is **no chat interface**. The agent takes instructions only from GitHub deployments.

## How a deployment triggers the agent

```
box: scripts/sync-data.sh ──git push main──▶ GitHub ──▶ Vercel Git integration builds + deploys (Production)
                                                         │
                     GitHub deployment "Production" ◀────┘  (Vercel creates it and reports state=success)
                                │
      repo webhook (deployment_status, HMAC-signed) ──POST /github/deployments──▶ eve custom channel
                                │  verify X-Hub-Signature-256, require state=success,
                                │  environment ∈ {Production, page-render}, repo = jessearmand/cybernetics-log
                                ▼
          from("deployment-<id>").send(prompt, auth = github-deployment service principal)   (one session per deployment)
                                ▼
          agent (deepseek/deepseek-v4.1-flash via AI Gateway):
            load_discourse_data → data/discourse.json + data/render-instruction.md at the deployment's commit
            publish_page        → deterministic HTML + agent copy → Vercel Blob (latest + archived per commit)
                                ▼
          GET /  (agent/channels/home.ts) serves the latest render
```

Why this shape (eve-native):

- eve's built-in [GitHub channel](https://eve.dev/docs/channels/github) handles comment invocations and `issues` / `pull_request` / `check_*` / `workflow_run` hooks, which are all anchored to an issue or PR thread. It has no `deployment_status` hook. A [custom channel](https://eve.dev/docs/channels/custom) (`defineChannel` + `POST`) is eve's documented way to accept any other signed webhook and start a session, so `agent/channels/github-deployment.ts` does exactly that.
- A plain repository webhook is enough. Vercel already creates a GitHub deployment for every push and marks it `success` when it goes live, so no GitHub Actions workflow or extra token is needed. GitHub signs every delivery with the webhook secret, and the channel rejects unsigned or mis-signed requests.
- [Schedules](https://eve.dev/docs/schedules) would add a non-deployment trigger, so the agent has none.
- The default `/eve/v1` session API (TUI, `useEveAgent`, curl) is disabled in `agent/channels/eve.ts`. Its routes return 404.
- The data is read from `raw.githubusercontent.com/<repo>/<deployment sha>/data/…`, so a render always uses the commit that triggered it, even if the webhook reaches a different build. The repo is public. If that read fails, the agent falls back to the copy bundled in the build and the page footer shows a warning.
- The tools refuse to run unless the session was started by the verified deployment channel (or by `eve dev` locally).

### Instructions

- **Default:** `data/render-instruction.md` at the deployment's commit. Edit it, commit and push, and the next production deploy re-renders with it.
- **One-off, no data change:** `scripts/trigger-render.sh "Lead with the pair test; accent teal."` creates a GitHub deployment in the `page-render` environment with `payload.instruction` and marks it successful. That instruction takes precedence over the file.

Preview deployments (branches and PRs) are ignored.

## Layout

```
agent/
  agent.ts                      model deepseek/deepseek-v4.1-flash, defaultTools: false, cost/time limits
  instructions.md               renderer role and rules (never classify, numbers only from data)
  sandbox.ts                    in-process just-bash sandbox (never used; avoids provisioning a Vercel Sandbox)
  channels/eve.ts               disableRoute(): no chat/session API
  channels/github-deployment.ts POST /github/deployments: signed deployment_status → render session
  channels/home.ts              GET / and HEAD /: serve the latest render (data-only placeholder before the first)
  tools/load_discourse_data.ts  data + instruction for the triggering commit (read-only)
  tools/publish_page.ts         render HTML from data + agent copy, store in Blob; ends the turn
  lib/                          config, webhook verify/parse, data loader, renderer, Blob store, session guard
data/
  discourse.json                condensed findings (generated by scripts/build_discourse.py)
  jev_labels.csv                per-post Jev labels/probabilities (+ hand labels for the 40-post sample)
  authors.json                  per-author model shares and hand reading
  hand_labels.json              40 hand labels (the ground truth: R 45% / C 25% / S 30%)
  jev_report.md                 full Jev write-up
  render-instruction.md         default render instruction
scripts/
  build_discourse.py            box → data/ (recomputes every derivable number from the label files)
  sync-data.sh                  build + check + commit + push (push to main ⇒ deploy ⇒ re-render)
  trigger-render.sh             manual re-render with an instruction (page-render deployment)
  sync-default-instruction.mjs  keeps the bundled default instruction in sync with the .md
test/                           node:test suites (webhook, renderer, data consistency)
.agents/skills/eve              eve agent skill (`npx skills add vercel/eve`)
```

## Regenerating the data from the box

The analysis lives on the box at `/workspace/consciousness`: the X collection, embeddinggemma-2 runs, Jev classification and hand labels. After re-running any of it:

```bash
cd /workspace/cybernetics-log
scripts/sync-data.sh                 # build data/, typecheck + tests, commit, push to the current branch
# or step by step:
npm run data:build                   # python3 scripts/build_discourse.py [/workspace/consciousness]
npm run check                        # tsc + node --test
git add data && git commit -m "data: …" && git push
```

`build_discourse.py` copies `jev_labels.csv`, `authors.json`, `hand_labels.json` and `jev_report.md`, and rebuilds `discourse.json`. It recomputes stance counts, accuracy, confusion matrices, confidence curves, per-cluster Jev mix and the key-account Jev labels from the label files. Facts that exist only in the prose reports are curated constants in the script: embedding-variant accuracy, the held-out two-question score, cluster themes and account blurbs. It uses the standard library only and never touches secrets.

Pushing to `main` deploys to production. When that deployment succeeds, the agent re-renders.

## Local development

Requires Node 24.

```bash
npm install
npm run check                     # typecheck + tests
npm run build                     # eve build
AI_GATEWAY_API_KEY=… GITHUB_DEPLOYMENT_WEBHOOK_SECRET=dev npx eve dev --no-ui
# simulate a signed webhook:
body='{"deployment_status":{"id":1,"state":"success","environment":"Production"},"deployment":{"id":1,"sha":"<40-hex sha on GitHub>","ref":"main","payload":{}},"repository":{"full_name":"jessearmand/cybernetics-log"}}'
sig="sha256=$(printf '%s' "$body" | openssl dgst -sha256 -hmac dev | sed 's/^.*= //')"
curl -X POST localhost:2000/github/deployments -H 'x-github-event: deployment_status' -H "x-hub-signature-256: $sig" -d "$body"
open http://localhost:2000/
```

Without Blob credentials, renders go to `.eve/rendered/`.

## Configuration

| Variable | Where | Purpose |
| --- | --- | --- |
| `GITHUB_DEPLOYMENT_WEBHOOK_SECRET` | Vercel (Production), **secret** | Must equal the GitHub webhook secret. Without it the route returns 503. |
| `BLOB_STORE_ID` / `BLOB_READ_WRITE_TOKEN` | Added by connecting a Blob store | Page storage. OIDC (`VERCEL_OIDC_TOKEN` + `BLOB_STORE_ID`) is used when available. |
| `PAGE_BLOB_ACCESS` | optional | `private` (default) or `public`; must match the Blob store's access mode. |
| `RENDER_ENVIRONMENTS` | optional | Default `Production,page-render`. |
| `GITHUB_REPOSITORY_ALLOWLIST` | optional | Default `jessearmand/cybernetics-log`. |
| AI Gateway auth | automatic | Vercel OIDC on deployments. Locally, `AI_GATEWAY_API_KEY`. No keys are committed. |

## Going live (one-time)

1. **Blob store:** in the Vercel project, Storage → create or connect a Blob store to `cybernetics-log` (Production). This adds `BLOB_STORE_ID` / `BLOB_READ_WRITE_TOKEN`. If the store is public, also set `PAGE_BLOB_ACCESS=public`.
2. **Webhook secret:** generate a random secret (`openssl rand -hex 32`) and add it as the sensitive Production env var `GITHUB_DEPLOYMENT_WEBHOOK_SECRET`.
3. **Deployment Protection:** the project has Vercel Authentication on for all `*.vercel.app` URLs, so GitHub's webhook would get a 401. Pick one option:
   - enable *Protection Bypass for Automation* and append `?x-vercel-protection-bypass=<bypass secret>` to the webhook URL; or
   - add a custom domain (it isn't protected under the current mode); or
   - narrow protection to previews only.

   The same choice decides whether the page itself is public.
4. **GitHub webhook:** in Repo → Settings → Webhooks → Add webhook, set:
   - Payload URL: `https://cybernetics-log-jessearmand.vercel.app/github/deployments` (plus the bypass query if used)
   - Content type: `application/json`
   - Secret: the value from step 2
   - Events: *Let me select individual events* → **Deployment statuses** only

   GitHub's initial `ping` should return 200.
5. Merge to `main`. The production deploy's `deployment_status: success` starts the first render. Check it under Vercel → Agent Runs / Logs, then open `/`.
